# 项目管理后台产品需求快速评审版

## 1 产品目标

开发一套仅供内部人员使用的独立项目管理后台，统一记录需求从提出到结项的全过程，并在测试环节集中管理相关 Bug。

产品重点解决以下问题：

- 明确每个需求的当前状态和当前负责人。
- 集中保存各环节的确认意见、截图、附件和操作时间。
- 分别记录测试验收、需求方验收、代码上传和代码审核。
- 需求返工后保留旧版本、旧结论和旧材料。
- 支持按项目、状态、人员和时间查询历史记录。
- 在测试环节集中记录 Bug，并跟踪开发修复和测试回归结果。

首期以记录和追溯为主，不建设复杂的强制审批系统。

## 2 用户角色

| 角色 | 主要职责 |
| --- | --- |
| 需求提起人 | 提交需求、确认整理后的需求、完成需求方验收 |
| 产品负责人 | 整理业务规则、原型、异常处理和验收标准 |
| 分配负责人 | 指定开发人员、任务范围和排期 |
| 开发人员 | 接单、开发、自测、修复 Bug 并登记代码信息 |
| 测试负责人 | 按验收标准测试、提交 Bug 并完成回归验证 |
| 代码审核人 | 审核指定版本的代码 |
| 结项人 | 检查资料完整性并确认结项 |
| 系统管理员 | 管理账号、角色、项目和操作日志 |

## 3 核心流程

1. 需求提出
2. 需求规范整理
3. 需求确认
4. 分配开发
5. 开发接单与实现
6. 测试验收
7. 需求方验收
8. 代码上传
9. 代码审核
10. 结项检查
11. 已完成

需求可以退回到相关的上游环节。退回时必须填写原因，并生成新的处理轮次，原有记录继续保留。

### 测试与 Bug 处理流程

1. 需求进入测试验收
2. 测试负责人执行测试
3. 发现问题时，在当前需求下创建 Bug
4. Bug 指派给对应开发人员修复
5. 开发提交修复说明和待验证版本
6. 测试负责人完成回归
7. 回归通过后关闭 Bug；不通过则重新打开
8. 当前需求下的 Bug 处理完成后，测试负责人填写测试结论
9. 需求进入需求方验收

Bug 默认关联当前需求、测试记录和测试轮次。回归不通过时重新打开，并保留之前的修复与回归记录。

## 4 核心页面

| 页面 | 主要内容 |
| --- | --- |
| 工作台 | 我的待办、逾期事项和最近更新 |
| 项目列表 | 项目负责人、进度、需求数量和逾期数量 |
| 项目详情 | 项目信息、参与人员、需求列表和进度统计 |
| 需求列表 | 需求编号、标题、状态、负责人、优先级和更新时间 |
| 需求详情 | 需求正文、当前环节、责任人、附件、版本和处理时间线 |
| 测试与 Bug | 测试结论、Bug 列表、严重程度、状态、负责人、修复版本和回归结果 |
| Bug 详情 | 关联需求、复现步骤、实际结果、期望结果、环境、附件、修复记录和回归记录 |
| 处理窗口 | 确认、退回、转交、处理说明和附件上传 |
| 后台管理 | 账号、角色、项目配置和操作日志 |

## 5 记录规则

- 每个需求生成唯一编号。
- 每个环节保存责任人、实际操作人、操作时间、处理结论和说明。
- 截图和附件必须标记所属需求、流程环节和处理轮次。
- 测试验收与需求方验收分别保存记录，不能相互覆盖。
- 代码上传与代码审核分别保存记录，并关联对应提交编号。
- 转交责任人后，保留转交人、原责任人、接收人、原因和时间。
- 需求退回后增加处理轮次，旧版本、旧结论和旧附件保持只读。
- 普通用户不能修改或删除历史处理记录。
- 状态变化、人员变更、字段修改和附件操作均进入操作日志。
- 首期不强制要求每个环节上传截图；资料缺失时允许继续，但必须提示并记录资料不完整。
- 每个 Bug 生成唯一编号，并自动关联所属项目、当前需求、测试轮次、发现版本和运行环境。
- Bug 必须记录复现步骤、实际结果、期望结果、严重程度、优先级和当前负责人。
- Bug 修复需要登记修复说明、代码提交编号和待验证版本。
- 每次回归都独立保存测试人、测试时间、测试版本、结果和截图；回归失败后重新打开 Bug。
- Bug 关闭后仍可重新打开，原有修复和关闭记录不得覆盖。
- 当前需求存在未关闭 Bug 时，系统提示风险；如仍确认测试通过，必须填写原因并保留记录。

## 6 首期范围

- 独立账号登录和账号停用。
- 项目、项目成员和需求管理。
- 测试环节内的 Bug 创建、分级、指派、修复、回归、关闭和重新打开。
- 固定流程及状态流转。
- 确认、退回、转交和补充记录。
- 需求版本、处理轮次及历史记录。
- 截图、文档和其他附件管理。
- 我的待办、逾期提醒和站内通知。
- 按项目、状态、人员、优先级和时间查询。
- 按严重程度、发现版本、修复版本和 Bug 状态查询。
- 基础角色权限和操作日志。

系统仅限内部人员使用，统一采用中文界面和独立账号。首期不接入企业微信、钉钉、企业邮箱、公司账号或其他企业平台，不建设多语言、流程设计器、逐环节强制审批和代码仓库自动同步功能。

## 7 待确认事项

- “已完成”是指代码审核通过，还是必须已经发布并可供用户使用。
- 是否需要增加“发布上线”和“上线验证”两个环节。
- 项目负责人是否允许代处理其他角色负责的事项。
- 附件允许的类型、单文件大小、总容量和保存年限。
- 系统统一使用哪个业务时区。
- 是否需要移动端适配。
- 需求作废、项目归档和附件删除记录需要保留多长时间。
- Bug 的严重程度和优先级分别采用哪些等级。
- 哪些角色可以确认 Bug、关闭 Bug 和重新打开 Bug。
- 是否需要支持测试流程之外发现的独立 Bug；首期默认 Bug 必须关联需求。
